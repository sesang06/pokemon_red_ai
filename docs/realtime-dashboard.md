# Pokemon Red Runtime Debugger

## Purpose

The runtime debugger is an optional observation surface for the existing
PyBoy, MCP, and Google ADK loop. It does not own a second emulator and does not
parse terminal log strings. The game remains the visual focus; supporting
panels expose current state, action verification, navigation, memory, and
structured events.

## Data Flow

```text
PyBoy ticker
  -> PokemonSession immutable observation cache
  -> latest-only dashboard listener
  -> LiveEventHub current state
  -> WebSocket snapshot / state_delta
  -> React + TypeScript debugger

Planner / Executor / Verifier / Interpreter / Memory
  -> runtime and trace callbacks
  -> LiveEventHub typed event history
  -> WebSocket event
```

State answers what is true now. Events answer what just happened. The browser
does not query PyBoy. A newly connected client first receives one complete
snapshot and then nested state deltas and typed events.

## Runtime Behavior

- Session snapshots are accepted through a nonblocking latest-only handoff.
- Web state emission is capped at 10 Hz; the emulator snapshot cache remains at
  its configured refresh rate.
- Subscriber queues and the shared event history are bounded.
- Slow or disconnected clients drop old transport messages, not game frames.
- Browser reconnect restores current state and up to 500 recent events.
- Planner event details expose only the selected structured action, relevant memory keys, and errors.
- The dashboard is disabled with `--no-dashboard`; startup failure is logged and
  gameplay continues.

## UI Surfaces

- Actual 160x144 PyBoy PNG frame with nearest-neighbor scaling
- Toggleable collision/coordinate overlay generated by the existing vision code
- Map, position, facing, mode, dialog, and battle state
- Current goal, status, attempt, step, action, and verification result
- Compact Planner -> Executor -> Verifier -> Interpreter -> Memory pipeline
- Existing visible world cells, current player, target, and planned path
- RAM-derived party, inventory, HP, level, and status
- Searchable and filterable structured event console with JSON detail
- Recent memory reads/writes and an opt-in RAM/StateDiff debug inspector

## Party Sprites

`PokemonRedMemoryReader` converts Pokemon Red's internal species index into a
National Pokédex `species_id` and retains the raw value as
`internal_species_id`. The frontend generates one deterministic URL:

```text
https://raw.githubusercontent.com/PokeAPI/sprites/master/sprites/pokemon/versions/generation-i/red-blue/transparent/{species_id}.png
```

No PokéAPI REST request is made. Normal browser caching handles repeated image
use, image rendering remains pixelated, and missing/invalid IDs fall back to a
neutral placeholder. Sources:

- https://github.com/PokeAPI/sprites
- https://github.com/pret/pokered/blob/master/data/pokemon/dex_order.asm

## Start

Production UI with the normal ADK agent:

```powershell
.\.venv\Scripts\pokemon-adk.exe
```

Open `http://127.0.0.1:8765`.

Frontend development:

```powershell
cd dashboard\frontend
pnpm install
pnpm dev
```

Production rebuild and tests:

```powershell
pnpm build
pnpm test
cd ..\..
.\.venv\Scripts\python.exe -m pytest
```

## Known Limits

- Sprite PNGs are remote static assets and require network access on first use.
- The map panel visualizes the existing visible-world-cell window, not a full
  decoded region map.
- The dashboard is observation-only; gameplay commands remain in MCP, the Qt
  control panel, or the agent executor.
- If a party slot is observed during the few frames in which the game is still
  constructing it, temporary zero HP/level values may appear and then update
  from RAM automatically.
